# 星际航运经营游戏

一款以星际客运网络规划为核心的网页经营游戏。

当前阶段是概念验证：验证玩家是否会享受观察需求、设计航线、配置船只，并在竞争和事件中持续优化运输网络的过程。

## 当前实现

项目目前由两个部分组成：可独立运行的 TypeScript 日结算模拟核心，以及使用 React、Vite、Three.js WebGPU 和 SVG 构建的网页概念验证界面。

模拟核心已经支持：

- 根据星港属性和理论旅行时间生成三类客运需求
- 将往返线和环线自动展开为可售服务航段
- 搜索最多两次换乘的候选行程
- 根据票价、时间、频率、换乘、舒适度、声誉和准点率分配客流
- 在多个市场之间分配共享航段运力
- 结算服务航段及公司的收入、成本和利润

### 本地运行

需要 Node.js `^20.19.0` 或 `>=22.12.0`；推荐使用 Node.js 24。

```bash
npm install
npm test
npm run demo
npm run demo:campaign
```

常用命令：

```bash
npm run check  # TypeScript 类型检查
npm run build  # 编译到 dist
npm test       # 编译并运行情景测试
npm run demo   # 运行三港口示例
npm run demo:campaign # 运行20星港、196日战役示例
```

模拟器的公共入口是 `src/index.ts`，完整日结算入口是 `simulateDay()`。

## 网页界面

网页端默认生成 8 个恒星系和 24 个星港。界面可配置 3–24 个恒星系、每个恒星系 1–6 个星港且总计不超过 60 个星港，并支持可复现种子、星域形状、超空间网络走向和航道密度配置。

当前网页功能包括：

- 可拖动的银河地图；每个语义尺度都有内容边界，越界拖动带阻尼并在松手后回弹
- 使用同一个连续地图视窗呈现“银河 → 恒星系 → 行星/卫星”；天体由一个透明 Three.js WebGPU 画布渲染，航道、轨道、标签、星港和交互热区由同步相机的 SVG 层渲染
- 普通滚轮缩放以鼠标所指的世界坐标为中心，使用 85ms 非线性缓动降低输入延迟
- 银河、恒星系与行星尺度使用互不重叠的合法缩放区间；跨过阈值后会锁定并完成与双击相同的居中深入动画，不会停在层级之间
- 航道、轨道、标签与细节会随缩放值逐渐显隐；同一世界坐标中的天体会连续改变位置和尺寸，不通过弹窗或独立地图打断层级切换
- 银河与恒星系层共享同一份 1 至 3 颗恒星数据，并显示行星轨道、卫星、随机星环、殖民地与星港位置
- 每颗行星和卫星拥有可复现的公转周期、自转周期、初始相位和自转轴倾角；播放时间时沿轨道连续运行，暂停后停止，表面自转使用降速后的视觉时间
- 恒星系与行星层共享深空背景；普通行星使用 TSL 程序化地形配色，气态和冰巨星使用独立的大气条带与湍流材质，并带有球面光照、大气边缘和可选星环
- 天体本体共享单个 Three.js WebGPU 渲染器；浏览器不支持 WebGPU 时自动回退 WebGL 2，渲染器初始化失败时保留 SVG 天体作为最终降级方案
- 恒星按 O–M 光谱型使用独立的 TSL 程序化光球材质，呈现对流颗粒、活动区、缓慢自转与外层辉光
- 行星和卫星的类型、人口（M/B）、殖民地、发展度、经济类型、公转/自转周期、自转轴倾角与星环数据
- 固定在顶部的当日收入、成本、利润、客流与可用资金
- 固定在底部的暂停、倍速和单日推进控制
- 发展度驱动的跨星需求，以及热门市场的额外 AI 竞争航线

```bash
npm run dev       # 启动本地开发服务器
npm run build:web # 构建静态网页到 web-dist
```

网页端目前在主线程同步执行单日结算，因此交互式生成器暂时限制为最多 60 个星港。后续迁移至 Web Worker 后可以进一步提高上限。

## TODO：距离第一版正式可玩模型的差距

第一版“可玩”的完成标准是：玩家能够从有限资金与舰队开始，观察市场，建立或修改航线，购买并分配船只，推进时间，根据财务、客流、竞争和事件反馈持续调整网络，并拥有明确的失败条件、阶段目标和存档能力。

优先级说明：`P0` 是形成最小可玩经营循环的阻塞项；`P1` 是达到第一版设计目标所需的完整系统；`P2` 是发布前的工程、平衡和体验保障。

### P0：玩家经营循环

- [ ] 建立可变且可序列化的游戏状态。目前网页每天都从生成场景重新结算，玩家不能永久改变航线、舰队、基地、声誉或公司资产。
- [ ] 实现航线规划界面：从地图选择起点、沿途停靠和终点，支持往返线、环线、正常停靠、技术停靠以及不进入星港的跳停。
- [ ] 在提交航线前验证相邻航段、推进方式、船型航程、最低港口等级和技术停靠可行性，并清楚显示失败原因。
- [ ] 实现航线预测：周转时间、平均班次间隔、每月座位、潜在与预计客流、满载率、收入、燃料/维护/人员/港口成本、利润，以及与已有航线的重叠和分流。
- [ ] 实现航线管理：启用、暂停、关闭、复制、反向环线、调整停站、增减船只、更换船型和修改三类客群价格策略。
- [ ] 将现有 `ShipType` 数据接入舰队系统：船型目录、购买、融资、出售、单船所有权、可用状态以及向航线分配/撤回船只。
- [ ] 让资金成为真实约束。当前“可用资金”只是初始资金加累计运营利润；还需结算购船、融资、利息、出售、基地投资和其他资本支出，并处理资金不足与破产。
- [ ] 增加玩家航线与舰队总览，使玩家能够从地图或列表快速定位亏损、过载、闲置和无法运营的资产。
- [ ] 推进一天后保留所有玩家决策，并只对新的游戏日进行增量结算，而不是重新构造不可变场景。

### P0：市场反馈与可解释性

- [ ] 将当前“选中星港的六个热门目的地”扩展为完整 OD 需求地图/矩阵，并可按经济、商务和高端旅客筛选。
- [ ] 为每条航线显示实际分段客流、上下客量、载客率、收入、成本、利润、未满足需求和被换乘旅客占用的运力。
- [ ] 增加市场份额和竞争对比：玩家与每家 AI 的票价、旅行时间、频率、换乘次数、舒适度、声誉、准点率和供给座位。
- [ ] 解释客流变化和失客原因，例如票价过高、班次不足、绕行、换乘过多、竞争者更快或市场运力过剩。
- [ ] 增加按日、月和航线查看的财务与客流历史图表，而不只显示当天值和累计总额。
- [ ] 让星港 `dailyCapacity` 真正限制运营并产生拥堵或拒绝新增班次；目前该字段和事件修正尚未参与运力分配。

### P1：船只、维护与人员

- [ ] 为单船记录船龄、累计飞行时间、磨损、当前位置、可靠性、可用率和维护状态。
- [ ] 实现节约、标准、预防性三档公司维护政策，并让它们影响费用、故障率、延误、安全评级和停场时间。
- [ ] 将现有按飞行小时计算的维护费用扩展为定期维护、故障维修和备用船替换流程。
- [ ] 建立抽象人员能力：船员、维修工程师、地勤、航线调度和基地管理人员。
- [ ] 实现招聘、培训预算和人员容量；人员不足应限制可投入船只、延长维护并造成延误。
- [ ] 将准点率和可靠性从当前静态输入改为由船况、维护政策、人员、港口拥堵、航行风险和事件动态计算。

### P1：基地与网络扩张

- [ ] 允许玩家选择初始基地，并在其他星港建设、关闭和升级基地。
- [ ] 实现基地的驻扎船位、人员容量、维护能力、调度能力、备用船和周转效率。
- [ ] 计算远离基地运营的人员调度、维护和可靠性惩罚，使中央基地、区域基地和前进基地形成不同网络策略。
- [ ] 将基地投资纳入现金流，并让港口等级、当地费用和市场机会影响基地选址。
- [ ] 增加本地与公司声誉；服务质量、准点率、取消、事件响应和长期经营应改变不同市场的需求份额。

### P1：动态世界、事件与 AI

- [ ] 为随机银河生成 6–10 类可复现事件。目前固定六星系战役有预设事件，但网页随机场景的 `events` 仍为空数组。
- [ ] 增加事件预警、开始、恢复和结束界面，并在地图、需求、燃料价格、港口容量、航行时间和航权状态中显示影响范围。
- [ ] 支持玩家为事件临时增派船只、开设临时航线或调整价格，并在事件结束后处理撤回与残余需求。
- [ ] 实现 3–5 家具有明确风格的 AI 公司。当前竞争航线只在生成星域时静态创建，AI 不会随时间作出决策。
- [ ] 让 AI 能识别市场、建立或关闭航线、调整票价和运力、更换船型，并对事件和玩家行动作出反应。
- [ ] 为 AI 行动提供可解释记录：进入市场的原因、价格/班次变化、玩家份额下降原因和运力过剩提示。
- [ ] 让燃料供应与价格随事件或市场变化，而不是除预设事件外保持静态。
- [ ] 设计公司成长节奏、阶段目标、评分和失败条件，例如资金耗尽、连续亏损或安全评级过低。

## 第一版范围

- 固定战役示例包含 6 个恒星系统、20 个星港；网页随机星域默认包含 8 个恒星系统、24 个星港
